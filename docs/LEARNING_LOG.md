### 第 10 步问答：UNION、team 与每轮递归的内容

- 你的问题：UNION 做什么？team 是否是 WITH 的结果？如果顶层人员有三个下属，每个下属还有下属，递归时 team 会变成什么？
- 解答：team 是 WITH 定义的公共表表达式（CTE）名称，可理解为本条查询使用的命名结果。递归项 `JOIN team` 每轮读取当前工作批次；外层 `SELECT FROM team` 读取最终累计结果。它不会在每轮都拿全部历史结果重新向下查。
- UNION：合并结果并按完整行去重；递归时还会排除与此前累计结果重复的行。UNION ALL 则保留重复行。递归来自 WITH RECURSIVE 和自引用，UNION 本身不意味着递归。
- 示例（只用于解释，未插入数据库）：P0001 的直属下属为 A、B、C；A 下属 A1/A2，B 下属 B1，C 下属 C1/C2；A1 还有下属 X。
- 种子查询：工作批次 A/B/C，累计 A/B/C。
- 递归第 1 轮：读取 A/B/C，产生 A1/A2/B1/C1/C2；累计加入这五人。
- 递归第 2 轮：只读取 A1/A2/B1/C1/C2，产生 X；累计加入 X。
- 递归第 3 轮：读取 X，无新下属，工作批次为空，结束。最终查询得到全部九名下属。
- 每个符号代表一整行（person_id、name、head_person_id），不是一个标量。父级 P0001 不在此例结果中。假设组织关系无环。
- 依据：PostgreSQL 17 官方文档 Recursive Query Evaluation，https://www.postgresql.org/docs/17/queries-with.html#QUERIES-WITH-RECURSIVE 。

### 第 10 步补充问答：这是广度优先还是深度优先？

- 你的判断：上述逐层扩展看起来是广度优先，还是仅为讲解简化？
- 解答：判断正确。PostgreSQL 的递归 CTE 使用工作表按批迭代，这里的层层扩展可理解为 BFS；不是沿一条分支到底再返回。计算方式与最终输出顺序分开理解：同层行顺序不保证，本例 ORDER BY person_id 也不保证按层展示。
- 深度优先排序：生成路径或 SEARCH DEPTH FIRST 排序列后 ORDER BY，可以按深度优先的顺序展示，不意味着把内部执行变为 DFS。
- 参考：https://www.postgresql.org/docs/17/queries-with.html#QUERIES-WITH-SEARCH-ORDER 。

### 第 12 步问答：View 是否就是保存的查询，能否展开到 FROM 后？

- 你的问题：SQL 基础较久未用；View 是否可以理解成一个查询子句？查询视图时，是否相当于把之前那段查询放到 FROM 后？
- 解答：对当前这种普通视图，可以理解成数据库中保存了名称和定义的查询。CREATE VIEW 把 AS 后面的查询定义保存成数据库对象；之后可像使用表一样在 FROM 中引用它，并选列、筛选或关联。
- 关于展开：逻辑上可以把视图名理解成一个子查询。但展开的是 CREATE VIEW 的 AS 后面那段完整查询，不是把 CREATE VIEW 命令贴到 FROM 后。子查询需要括号和别名。实际由 PostgreSQL 解析、重写和优化，不能理解成客户端在做简单的字符串替换。
- 本例：视图内部先定义 WITH RECURSIVE chain，再 SELECT * FROM chain；对外暴露 root_id、target_id、depth、path、is_cycle。外层 WHERE root_id='P0001' 从其逻辑结果筛选起点，优化器实际执行不一定先完整计算所有起点。
- 保存的是什么：当前普通视图保存查询定义，不保存一份独立的人员结果数据；物化视图是另一类对象，暂不展开。

### 第 13 步插问：递归视图的 is_cycle 怎样赋值？

- 问题：回看 management_closure，想理解是否存在循环的字段如何计算。

### 第 20 步逐段讲解：本人来源与 JOIN USING

- 先前讲解：visible_people 的 self 分支将 identity_map 与 people、role_policy 连接，为账号生成“可查看本人”的关系。人员、策略都匹配才有结果。kind/reason 描述来源，priority 是来源展示排序，不是允许/拒绝优先级。本人规则固定存在，最终仍受 graph_valid 检查。
- 当前问题：USING 是什么意思？
- 解答：JOIN ... USING(role_key) 是连接两侧同名列做等值匹配的简写。当前左侧 identity_map 提供 role_key，右侧 role_policy 也提供 role_key，因此等价的行匹配条件是 ON i.role_key = r.role_key。
- 例子：映射的 role_key=manager，只匹配策略表中 role_key=manager 的行；当前是内连接，没有匹配的策略就不产生结果。
- 列输出区别：使用 SELECT * 时，USING 会把这一对连接列合并输出为一列；ON 通常保留左右两列。因此说“连接匹配条件相同”，不把所有场景的输出列结构都说成完全相同。
- 边界：USING 本身没有特殊授权含义；若两边列名不同，应使用 ON 明确匹配。也可 USING(a,b) 同时要求两列匹配，本轮先不扩展练习。

### 第 1 步问答：打开连接的终端命令是什么意思？

- 你的问题：为什么命令前要设置 `DOCKER_HOST`？为什么这个值是文件路径？在另一台 Linux 服务器上，先 `docker ps` 找到名字，再 `docker exec ... psql ...` 就能连接，为什么不用设置？
- 解答：整条命令有两层连接。电脑上的 Docker 命令先联系 Docker 引擎，让它在指定容器里运行 `psql`；容器里的 `psql` 再连接 PostgreSQL。
- `DOCKER_HOST=unix://$HOME/.colima/hr-superset/docker.sock`：告诉 Docker 客户端使用本机 Colima 的 `hr-superset` 实例。它是 Docker 引擎的 Unix socket 地址，不是 PostgreSQL 主机地址；`$HOME` 是当前用户的主目录，`unix://` 表示使用本地 Unix socket。写在命令前只对这一条命令生效，不修改全局 Docker context。
- Linux 上直接执行可以成功，说明 Docker 客户端已经能通过现有默认配置找到目标引擎。常见默认地址是 `/var/run/docker.sock`，也可能由 context 或环境变量指定，所以不需要每条命令再写 `DOCKER_HOST`。是否需要指定，取决于当前 Docker 配置，不是所有 Mac 必须写、所有 Linux 都不用写。
- `docker exec`：在一个已经运行的容器里执行命令。`-it` 保留交互输入并分配终端；`hr-superset-lab-postgres-1` 是容器名，不是数据库名。
- `psql -U postgres -d postgres`：启动 PostgreSQL 命令行客户端，以数据库用户 `postgres` 连接数据库 `postgres`。这两个相同的单词分别是用户名和库名。这里未写 `psql -h`，客户端在本容器配置下连接本地 PostgreSQL；前面的 `DOCKER_HOST` 不负责选择数据库服务器。
- 你说的 Linux 操作顺序是正确的：`docker ps` 列出运行容器，取 `NAMES` 列的容器名或容器 ID，再 `docker exec -it <容器名> psql -U <数据库用户> -d <数据库名>`。本机查看同一套容器时，也应给 `docker ps` 指定同一个 `DOCKER_HOST`。
