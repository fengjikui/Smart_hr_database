# 真实数据接入约定与权限需求

假设记录日期：2026-09-14。依据用户当前理解及本地 `infomations/` 资料整理，作为可调整的演示约定；尚未经业务方正式确认。

本文记录下一阶段真实数据接入的约定。当前演示仍使用 SQLite 合成数据、既有权限计算和查询计划；本文没有表示 PostgreSQL 或新增权限继承已经实现。

## 暂定的演示数据约定

| 项目 | 本阶段约定 |
| --- | --- |
| 首要服务对象 | HR 部门；主管查询是扩展使用场景。 |
| 数据库 | PostgreSQL。 |
| 数据入口 | 暂视为一张人员宽表；底层可能来自多表关联或加工，本阶段不追溯加工实现。 |
| 一行的含义 | 暂按一名员工的一条当前记录处理。 |
| 人员主键 | `person_id`；物理类型待实际表结构确认。 |
| 工号 | `employee_no`；保留前导零，按标识符处理，不转换为整数。 |
| 企业人 ID | `employee_id` 本阶段忽略，不参与人员匹配和授权。 |
| 直接主管 | `head_person_id` 暂关联同表 `person_id`。 |
| 部门主管 | `dept_master_id` 按本次主管 ID 约定关联同表 `person_id`；是否作为独立授权来源仍待确认。 |
| 部门 HRBP | `dept_hrbp_id` 暂关联同表 `person_id`。 |
| 历史任职与汇报线 | 不保留；仅有当前关系。 |

263 对字段的顺序对照见 [中英文字段对照](REAL_SOURCE_FIELDS.md)。字段对齐不等于确认其物理类型、加工公式、敏感级别或全部查询能力。

OA 用户的工号应先映射到宽表 `employee_no`，获得 `person_id` 后再计算人员权限；不能把示例工号直接当作 `person_id`。未匹配或多重匹配时应停止授权并提示修复映射。

## 暂定的演示人员权限含义

1. 员工可以查看本人；主管可以查看所有层级的管理线下属。
2. HRBP 可以查看本人以及 `dept_hrbp_id` 指向自己的人员。
3. 主管继承其下属可查看的人员范围，包括下属的 HRBP 服务范围。
4. 用户当前理解的案例预期：王承哲通过管理姜姜，可以查看姜姜服务的王灏和冯基魁；后续以业务沟通结果调整。

服务对象以 HR 为主，不等于所有 HR 员工默认拥有全公司人员权限。授权范围依旧通过上述具体关系计算。

### 拟采用的计算表达

以下是根据暂定演示规则整理的实现方案，尚未落入当前执行代码。

- `R(u)`：用户 `u` 本人，加上沿 `head_person_id` 反向遍历得到的全部管理线下属。
- `H(x)`：所有 `dept_hrbp_id = x.person_id` 的员工。
- `V(u) = R(u) ∪ ⋃[x ∈ R(u)] H(x)`：本阶段的可见人员集合。

该表达分别处理管理关系与 HRBP 服务关系，并将服务范围沿管理线上传。HRBP 可见某员工，不因此自动获得该员工本人的全部权限；对服务对象再次展开其下属需要另行定义业务规则。

实现中需按 `person_id` 去重，记录每位人员可见的来源：本人、管理线、本人 HRBP 服务或下属 HRBP 服务。管理链中的循环属于异常；HRBP 指向本人可以是合法业务数据，不能与管理环混为一谈。

“所有层级”表示没有人为业务层级截断；遍历仍须检测循环并保证能结束。关系变化后应刷新授权集合及版本，旧调试记录、看板与后续查询重新检查授权。此处的刷新是后续实现要求，当前模拟闭包尚没有真实源同步能力。

这里约定的是人员行范围。敏感字段、导出、角色能力和部门主管的额外授权来源，仍与人员范围分开定义；不能通过继承人员集合自动继承尚未批准的全部功能。

## 历史问题的处理边界

当前真实源不保留历史任职与汇报线，不能重建过去某日的实际部门或管理关系。

| 问题 | 处理约定 |
| --- | --- |
| 我现在能查看谁 | 使用当前管理关系与 HRBP 服务关系。 |
| 过去一段时间入职或离职的人数 | 若日期字段及对应人员记录仍保留，可以按选定的日期口径统计；记录保留范围待确认。 |
| 历史入离职按目前部门分组 | 可以作为明确标注的统计方式；不得暗示是事件当时部门。 |
| 历史入离职按发生时的部门分组 | 当前资料不足，需历史任职数据；不能默认用当前部门替代。 |
| 某主管去年当时的下属 | 当前资料不足，不能重建当时汇报线。 |

现有模拟库具有历史任职样例，与本次真实源能力不同。接入时应调整能力说明和验收用例，避免把模拟库的历史组织能力当作真实源已经具备。
